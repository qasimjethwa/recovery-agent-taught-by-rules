# Recovery Agent, Taught by Rules

**Lexsi AI Safety and Alignment Hackathon — Track 3: Agentic Fine-tuning**
**Builder:** Qasim Jethwa

Fine-tuning **Aya Expanse 8B** (Cohere Labs) to execute failed-payment recovery plans with reliable tool calls — taught and audited by a deterministic rule engine that already ships in production-style use: **[Recovery Copilot](https://github.com/qasimjethwa/Failed-payment-recovery)**.

---

## The idea

An agent that acts on payments can do real damage with a wrong tool call: messaging a customer about a bank-side error, retrying at the wrong moment, offering the wrong rail. Recovery Copilot — a rule-based engine that classifies each payment failure and prescribes the exact recovery action, channel, delay and message — is deterministic enough to be a **teacher** (it generates tool-calling tasks with answers that are correct by construction) and a **verifier** (it grades any agent against that same ground truth). This entry uses it for both: AgentTune-style fine-tuning on its tasks, AuditKIT-style evaluation of the result.

## Pipeline

```
Recovery Copilot rule engine (shipped, deterministic)
        │  faithful Python port
        ▼
data/generate_dataset.py ──► train.jsonl (400) ──► train/train_lora.py ──► LoRA adapter (Aya Expanse 8B)
        │                    eval.jsonl  (128) ──► eval/evaluate.py ────► before/after audit (4 metrics)
        └─ oracle.py: independent re-implementation that cross-checks the port
```

## The dataset (real, generated by the shipped script)

- **Train: 400 cases** — balanced, 50 for each of the 8 failure reasons (insufficient funds, OTP timeout, bank server error, card declined, network drop, incorrect CVV, expired card, daily limit exceeded).
- **Eval: 128 held-out cases** — a different, natural mix (bank server error 17, card declined 24, OTP timeout 19, insufficient funds 15, network drop 15, daily limit exceeded 14, expired card 13, incorrect CVV 11), including 8 edge cases where UPI is the original method and the bank-error silence rule is exercised.
- Transaction IDs are **disjoint across splits (0 overlap, asserted in code)**; 243 gold tool calls and 757 gold argument values in the eval split.
- Each case: a failed-payment scenario, 4 available tools (`schedule_retry`, `send_customer_message`, `offer_alternate_method`, `silent_retry`), the gold call sequence (1–3 calls), and the expected recovery decision.

Regenerate with `python3 data/generate_dataset.py`.

## Harness verification (actually run, 2026-10-23)

Scoring the oracle's predictions on the eval split with `eval/evaluate.py`:

| Metric | Oracle | Corrupt control |
|---|---|---|
| Tool-call exact-match accuracy | 1.0000 | 0.9218 |
| Argument accuracy | 1.0000 | 0.9749 |
| Invalid-call rate | 0.0000 | 0.0000 |
| End-to-end task success | 1.0000 (128/128) | 0.7188 (92/128) |

The oracle is a *second, independent* implementation of the engine agreeing with the dataset generator on all 243 calls — that validates the port and the scorer. The control run (wrong channel on OTP cases; customer wrongly contacted on bank-error cases) drops to 0% success in exactly those two classes, proving the audit catches the errors it exists to catch. **Neither number is a model result** — the base model's baseline and the tuned model's scores are measured in-window (below).
